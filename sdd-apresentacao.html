O problema

Código sem spec vira decisão sem memória.

O SDD transforma cada mudança relevante em um artefato rastreável: por que mudou, o que mudou e como foi validado — antes de tocar no código.

Sem SDD

  • Prompt solto → agente assume stack, escopo e convenções
  • Decisões de design sem registro; contexto morre no chat
  • Review reativo, no fim, quando o custo do erro já é alto

Com SDD

  • Fases numeradas: research → specify → plan → execute → review
  • Pasta specs/ versionada: As Is, To Be, plano, execuções e gates
  • Gate de review por task e Iron Law contra fix sem verificação

01

New

Abre a mudança rastreável: lê a issue, cria a pasta da spec, define TDD e feature flag, sugere a branch.

02

Research

Mapeia o As Is — código e documentação — na spec ativa.

03

Specify

Define o To Be junto com o dev, em brainstorming: goals, critérios de sucesso, non-goals, restrições e edge cases.

04

Plan

Backlog executável zero-context: interfaces, mapa de arquivos, steps bite-sized e dependências.

05

Review

Revisão humana da spec + plano — o dev aprova antes de escrever qualquer linha de código.

06

Execute

Implementa a task/fase e roda o loop implement → review → receiving-review → fix. Worktree opt-in.

07

Spec review

Valida se goals e user stories foram atingidos após todas as tasks.

08

Docs

Atualiza a documentação pública e preenche o mr-template.md; encaminha para finish-branch.

Contexto isolado · menos alucinação, menos tokens

Registro em disco = execução em contexto limpo.

Porque spec, tasks e execuções ficam escritos e versionados, cada fase ou task roda em contexto próprio — lendo só o artefato que precisa, não o histórico inteiro do chat.

Fonte escrita & verificada
spec.md · As Is → To Be
tasks.md · zero-context, bite-sized
executions.md · gates & decisões
Subagente readonly
contexto: só a spec + o finding
Worktree isolado
contexto: só a task + interfaces
Nova sessão / outra fase
contexto: só o artefato relevante
Menos histórico à deriva → menos alucinação e menos tokens. Cada rodada lê só o artefato que precisa — não a conversa inteira —, gastando uma fração dos tokens de contexto. E como o registro vive em disco, tasks independentes rodam em paralelo e a execução fica reproduzível.
Genérico por design

As skills não sabem nada do seu projeto.

Contrato único

Stack, comandos de build, issue tracker, integrações e branch base vivem no AGENTS.md do repositório — não hardcoded na skill.

Bootstrap automático

/sdd-init analisa o repositório, detecta as convenções e gera AGENTS.md, CLAUDE.md e GEMINI.md. Idempotente: preserva edições e preenche lacunas.

Fase 06 · o coração

Execute é um loop, não um disparo.

1

Implementar

Subagente escreve só o plano aprovado. Orquestrador não coda.

2

Spec compliance

Revisor readonly — bate o resultado contra a spec.

3

Code quality

Revisor readonly (+ agente code-reviewer) avalia o código.

4

receiving-review

Filtra findings: aceito / rejeitado / ambíguo. Gate obrigatório.

5

Fix → repete

Só findings aceitos viram fix. Loop até aprovar ou escalar.

Iron Law · review interno
NENHUM FIX DE APONTAMENTO DE REVIEW SEM PASSAR POR receiving-review
Findings dos estágios 1 e 2 são hipóteses — verificadas no código antes de qualquer alteração. Nada de fix reativo.
Skills transversais

Disciplina que atravessa todas as fases.

tdd

TDD condicional

Red → green → refactor com Iron Law. Só quando tdd: true.

debugging

Causa raiz

4 fases + instrumentação multi-camada antes de qualquer fix.

verification

Evidência

Rodar o comando, ler o output — só então afirmar sucesso.

worktrees

Isolamento

git worktree opt-in no Execute; protege o checkout atual.

parallel-execution

Paralelismo

Tasks independentes via subagentes isolados.

receiving-review

Filtrar review

Entender → verificar → pushback → só então implementar.

finish-branch

Fechar ciclo

Menu: merge, abrir MR/PR, manter ou descartar branch.

commit-message

Commits

Conventional Commits, com a chave do issue tracker.
